# Architecture

## Components and responsibilities

| Component | Responsibility | Does NOT do |
|---|---|---|
| Kafka Connect (SpoolDir) | Reads dropped CSV files, emits JSON (all string fields), key = `user_session` | Type conversion, cleaning |
| Kafka | Durable ordered log in 3 partitions (ordering per session), decouples ingest from processing | Business logic |
| Spark Structured Streaming | Parse, safe-cast, apply quality rules, quarantine, features, dedup per batch, load, write ledger | Aggregation (done in ClickHouse) |
| ClickHouse | Fact table, quarantine, ledger, materialized-view aggregates, views | Streaming |
| Airflow | Supervises finite, checkable tasks and records evidence | Triggering micro-batches |
| Superset | Reads aggregate tables and views | Writes |

## Data flow

1. A CSV is copied into `data/connect/input` as `.tmp`, then renamed `.csv` (never a partial file).
2. Connect parses it (schema from the header, every field a string) and produces JSON keyed by `user_session`.
3. Spark reads micro-batches. Stage 1 parses JSON with an all-string schema. Stage 2 casts with `try_*` functions (Spark 4 runs in ANSI mode, so plain casts would crash the stream). Stage 3 evaluates ordered quality rules.
4. `foreachBatch`: skip if the batch's Kafka offset ranges are in `batch_ledger`; dedup identical events within the batch; write valid rows, quarantined rows, then the ledger row (last).
5. ClickHouse materialized views update the aggregates on each insert.
6. Superset queries aggregates. Airflow checks, reconciles, and repairs.

## Decisions and alternatives

| Decision | Chosen | Alternative | Why |
|---|---|---|---|
| Ingestion | Kafka Connect SpoolDir | Custom Python producer | Declarative, tracked offsets, no code to maintain. Cost: one more JVM container, one task per file, no throttle |
| HDFS | Not used | CSV -> HDFS -> Spark | Kafka is the durable buffer and ClickHouse the durable store. One datanode gives no fault tolerance, so HDFS would add 2 containers and a second copy of the data for no benefit |
| Stream engine | Spark Structured Streaming | Flink | Course requirement (Scala + Spark SQL), batch/stream unification, official ClickHouse connector. Cost: micro-batch latency of seconds |
| Storage | ClickHouse | PostgreSQL, Cassandra | Columnar scans read only needed columns. Postgres is row-oriented OLTP. Cassandra has no ad-hoc aggregation |
| Aggregation place | ClickHouse materialized views | Spark stateful aggregation | Exact, cheap, always current. Spark state for 9M+ sessions would be memory-heavy. Spark windows kept only as a demo |
| Dedup | ReplacingMergeTree + in-batch dedup + ledger | Spark global dropDuplicates | Bounded state. Eventual dedup is acceptable because aggregates can be rebuilt |
| Delivery | At-least-once + ledger | Exactly-once | Connector cannot set per-insert dedup tokens (not confirmed). Ledger skips replayed batches |
| Spark version | 4.0.x | 3.5 / 4.1 | Newest line the ClickHouse connector supports (0.9.0 lists Spark 3.3-4.0) |
| Airflow role | Orchestrator of finite jobs | Run Spark from Airflow | Streaming is a continuous service. Airflow checks, loads, reconciles, repairs |
| BI source | Aggregates + views | Raw table | Dashboard reads thousands of rows, not tens of millions. Two distinct-count cards are the documented exception |

## Delivery semantics

Kafka offsets are recorded in the Spark checkpoint (`offsets/N` before processing, `commits/N` after the sink returns).
A crash between them re-runs batch N. The ledger row (written last) makes the re-run a no-op when the crash happened
after the ledger write. Residual risk: a crash between the data insert and the ledger insert, and changing the batch size
before replaying. Both create duplicate rows that the raw table collapses at merge time, but the aggregates
double-count them until `rebuild_aggregates` runs. Detection is `reconcile.sql` / the `data_quality` DAG.

## Resource model

Compose profiles (`ingest`, `process`, `job`, `orchestration`, `bi`) keep a 10 GB WSL workable. Memory caps are ceilings,
not reservations. Peak usage per container is in `docs/performance.md`. Everything at once needs more than 10 GB.

## Security posture (development scope)

Secrets live in `.env` (gitignored), generated by `scripts/init-env.ps1`. Superset uses a read-only ClickHouse user with
query time and memory limits. Listeners are plain text and the stack is meant for localhost. Production would need TLS,
authentication on Kafka and Connect, a secrets manager, replication, and backups.
